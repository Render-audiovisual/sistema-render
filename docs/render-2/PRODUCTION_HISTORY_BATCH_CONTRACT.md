# Historical production review, version 2

Local implementation, integration102. This does not authorize migration of a configured database or production deployment.

## Scope and compatibility

The principal Express/PostgreSQL application now accepts an explicit review of several historical editing tasks and selected videos in an existing or new production visit. The069/070 receipts remain unchanged. Version1 reconciliation remains available; no automatic backfill, name matching, splitting of aggregate scripts or inherited approval is performed.

Migration078 adds `produccion_revision_lotes`, its selected videos and original-task dispositions, and immutable video/task mappings. It retires only the015 aggregate-only unique index on `origen_visita_id`, replacing it with a nonunique lookup. The059/060 per-video canonical task uniqueness and restrictive mapping FKs remain. This permits several deliberately identified original children, not duplicate tasks for one video. Current legacy confirmation creates no editing tasks and does not depend on015 `ON CONFLICT`.

## API

- Admin-only `GET /api/producciones/reconciliaciones/lotes/origen/:sourceId` returns version2, allowlisted source content, current visit/videos or null, all original child identities/versions/eligibility, and an opaque observation hash. It never returns raw task metadata or financial bags.
- Existing `POST /api/producciones/reconciliaciones`, with `version:2`, dispatches the batch service. See `validateProductionHistoryBatch` in `backend/src/production-history-batches.js` for the closed wire schema.
- The request contains a stable request UUID, expected source/visit revisions and context hash; selected existing video UUIDs or manually entered new-video fields; `adopt_original` with an exact original task ID or `manual_independent`; and every observed child's explicit `mapped`/`preserve_unmapped` decision with a reason.
- Global acknowledgment is `correspondencias_revisadas_manualmente`. The UI also requires a per-video acknowledgment, including explicit noninheritance of any historical evidence for independent videos.
- The response contains only reconciliation ID, visit ID, selected video IDs and `created`. Same actor/request/body replays the original receipt; different body returns409. A replay never restores old state.

## Identity, locks and atomicity

Server authority checks the current stable actor ID, active DB role and session epoch. A browser profile selector is not authorization. The actor/request mutex precedes the global objective lock, applicable objective-period locks, all discovered source/original/current tasks in ID order, then visit/videos. Observations and the complete original-child set are reread after locks; stale intent fails409 without a partial audit or mapping.

An existing visit's client/date/content/participants are not overwritten by review. New visits receive only explicitly entered fields plus the source client/date. Reviewed visits retain the existing protection against changing source date/client dimensions. Normal editing revisions and live evidence remain on original tasks. Mapping never copies deliveries, decisions, approvals, comments or publication events and does not create editing tasks.

## Live evidence and editorial continuation

Only the newest batch selecting a particular video supplies its proof. An invalid newest proof is terminal: no fallback to an earlier batch or069/070. Without any batch selection, legacy verification remains unchanged. An unrelated later child does not revoke other reviewed videos; an unselected/new video inherits nothing.

Original adoption preserves the exact task/video/visit/client identity and live operational domain. Independent videos can use ordinary per-video dispatch. Editorial discovery has a separate provenance-only helper: visibility is not dispatch permission. Association checks locked selection/CAS/lineage and writes the actual canonical tuple inside the transaction, then verifies strict historical proof before commit. Any failure rolls back the tuple and any newly created empty-slot publication. Canonical `administracion` tasks generated by `/piezas` are allowed for independent videos only on that exact live editorial tuple before normal handoff converts them to editing. Adopted originals remain editing tasks. Even an existing-task handoff replay rechecks strict live proof.

Finishing or approving an editing task never records a real publication. Visit date and editing deadline remain distinct.

## UI, recovery and limitations

The shared `ProductionHistoryBatchReview` appears in canonical Productions visit detail and the existing task reconciliation panel for historical/mixed contexts. Nothing is persisted to localStorage. No video or task is preselected by title/count/order. Unselected videos, photographs and unmatched original tasks are preserved.

The controller pins rendered session/source/lifetime, blocks duplicate clicks, freezes the submitted serialized body/UUID after dispatch and offers explicit identical-request verification after an uncertain outcome. A definite conflict requires an explicit fresh context and renewed acknowledgments; it never silently rebases. Shared navigation and parent production writes honor dirty/busy guards. Closing a dirty form asks to discard.

Drafts are memory-only, not cross-device recovery receipts. A forced browser escape may lose the draft; the backend receipt remains. Historical tasks that aggregate several videos must be preserved for specific manual disposition, not claimed as independent approvals. Automatic source transfer, financial edits, provider/Drive integration changes and deployment are outside this integration.

## Reproducible local validation

Use `RENDER2_RUN_LOCAL_INTEGRATION=true node --test --test-concurrency=1` with the production registry, editorial, reconciliation, adoption, batch-upgrade and history-batches integration files. The guarded harness creates fresh identity-checked temporary PostgreSQL clusters; it never reads the configured database URL. Pure suites use `node --test test/*.test.js` from backend; frontend tests and Vite build are separate gates.

The populated-upgrade test verifies unchanged originals before explicit review and a real second-child PostgreSQL lock wait followed by409 after a concurrent revision. The independent history-batch journey verifies live original deliveries/reviews, exact replay, mixed preservation, stale-proof and SQL-failure rollback, editorial entry and per-video handoff. See STATUS integration102 for final terminal totals and native-browser evidence, rather than treating compilation as complete master acceptance.
