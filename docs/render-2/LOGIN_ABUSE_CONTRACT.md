# Principal login abuse protection — local integration contract

Goal: close unlimited password/Google authentication attempts without replacing verified identities, credentials, bearer transport or existing session revocation. No real account provisioning, provider call, production access or deployment. Existing App/Vite/preview dirt stays outside this integration. Superpowers and Security Best Practices guide bounded input, durable concurrency and fail-closed behavior.

## Policy and API

Password login accepts a plain nonarray JSON object with only usuario/password, both strings; trimmed identifier1..320 UTF-8 bytes (no controls), password1..1024 UTF-8 bytes, no trimming or altered password semantics. Google accepts only credential string1..16384 UTF-8 bytes. Invalid shape/type/bounds400 generic error, before SQL/bcrypt/provider. Small auth body parser limit32kb before the existing general parser prevents parsing15mb at auth paths; malformed/oversized JSON yields safe400/413, no credentials logged. Valid input reserves a durable attempt before user lookup/bcrypt/provider. No automatic retry in frontend.

Limits:120 attempts per directly connected peer per15-minute fixed window, shared across both login methods; password additionally20 attempts per normalized identifier per15 minutes across peers. All attempts (including successful) count, bounded to limit+1, avoiding release/reset races and login-result leaks. Normalization trim/lowercase only, same as existing login lookup; keep existing unambiguous aliases for compatibility in this change. Identifier aliases may have independent buckets; peer bound still shared. Not a distributed-bot solution or complete account/SSO hardening. Account-targeted denial-of-service/shared-NAT effects require staging policy review. No permanent account lock or user-row changes.

`reserveLoginAttempt(pool,{peer,identifier?},secret)` returns `{allowed:boolean,retryAfter:positiveInteger}` after commit. Hash keys with built-in HMAC-SHA256 using server JWT secret, domain separation for peer/identifier; never persist raw identifier/IP/password/Google credential/token. Direct socket remoteAddress only, ignore forwarded headers/trust-proxy guesses. Normalize IPv4-mapped addresses and equivalent valid IPv6 forms; missing/invalid peer uses one shared fail-closed sentinel bucket rather than spoofable input. HMAC secret missing/invalid503, no fallback/raw hash key; secret rotation changes rate keys and is an operational reset gate.

Forward067 adds only `auth_login_buckets(bucket_key TEXT PRIMARY KEY,attempts INTEGER NOT NULL,window_started_at TIMESTAMPTZ NOT NULL,expires_at TIMESTAMPTZ NOT NULL)` with key64-lower-hex, attempts1..121 and expiry>start checks, expiry index. No FK or user/business/history mutation/backfill. Startup asserts relation column shape without running migration. All workers/processes share this DB state. Same ordered key lock/upsert transaction (READ COMMITTED), database clock, atomic expiry reset, bounded increments; no JS clock or in-memory rate cache. A blocked reservation still commits bounded counters, never rolls back its denial. Each reservation prunes at most100 expired rows via a bounded SKIP LOCKED selection in the same transaction, never live windows. No unbounded maintenance loop/timer. Release pool clients on every path; rollback errors preserve initial failure. Storage error fails closed503 before verification, no fallback to unlimited login. Do not log raw SQL parameters/errors with credential content.

429 closed `{error:'Demasiados intentos de acceso. Esperá unos minutos y volvé a intentar.'}` with integer Retry-After and Cache-Control:no-store (all auth responses no-store). Retry-After is max remaining seconds of denied buckets, minimum1. Missing storage/config returns generic503. Preserve generic401 wrong password/ambiguous alias/inactive account. Google configured failure semantics and authorized success DTO unchanged. Health/preflight/protected business routes not throttled by this policy. This is not cookie/CSRF migration, password hashing overhaul, notification-email alias removal or automatic real-user split.

## Ownership and verification

Accepted review gate: storage acquisition is bounded2s and late-acquired clients released; transactions set local lock_timeout1s and statement_timeout2s, without mutating global pool configuration. No request-scoped promise timeout may leave active statements/clients running unobserved. Window expiry is decided using database clock after row serialization, not a captured pre-wait application time. Reverse-proxy peer aggregation remains an explicit deployment-policy gate.

Final storage detail: each driver query also has3s query_timeout to bound missing network replies; rollback is bounded and uncertain failed clients destroyed. Cleanup candidates use stable database CURRENT_TIMESTAMP (transaction-start cutoff) so expiry index is usable; later safety rechecks and authentication window reset use actual database clock after serialization. Cleanup may intentionally leave just-expired rows until the next request, never extend an authentication window. Current keys acquire ordered advisory locks first; cleanup uses try-only advisory locks then SKIP LOCKED row locks, avoiding deletion of a key another reservation already owns. Hash-lock collisions can cause bounded unavailability, not extra allowed attempts. This is not a universal end-to-end5s SLA under every fault; actual lock-fault case must return below5s in the isolated test.

Resource guard: at most32 unresolved pool acquisitions per process/pool. A request timing out does not free that resource slot until the original pg acquisition actually settles; further attempts fail503 rather than creating an unlimited pending queue during DB outage. A WeakMap may track only this local resource capacity, never business data or durable abuse counters. Late-client release/rejection drains slots and permits recovery. Multiple processes still share durable attempt windows; local resource caps are not a substitute for operational admission control/edge protection.

Coordinator owns server.js/router ordering, input helpers, startup-schema/harness integration, old-suite compatibility and final execution. Backend worker owns new login-abuse.js/unit tests only. Schema worker owns067 and schema test only. QA worker owns new real HTTP/PostgreSQL integration test and QA doc only. Independent reviewer read-only. No other simultaneous edits to shared files.

Actual fresh guarded PostgreSQL: exact thresholds under concurrent calls and independent clients, restart/module independence, expiry reset, valid login normal DTO and revocation, unknown/inactive/ambiguous and malformed credential failures, forged forwarded headers cannot evade, both login methods share peer (Google missing config never contacts provider), no token on429/503, unrelated business/session/user records unchanged, missing table fails closed then restore fixture only, populated066→067 additive invariance and actual persisted privacy. New schema is not applied to existing DBs. Existing snapshots that intentionally compare business rows across login must explicitly exclude only this new authentication-security table, not weaken operational invariance. All principal regressions, build, and bounded login browser UX if applicable. Test-only SQL time manipulation on owned fixture is not a production reset endpoint.
