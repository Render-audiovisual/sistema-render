# Approval of a concrete editing delivery

Prospective local contract, not rollout evidence. Preserve065 immutable deliveries, task/goal IDs, material/reference, original timestamps and historical approvals. No backfill or automatic editorial publication.

Both existing task approval entrypoints (PATCH task estado=aprobada and POST aprobar-publicacion) must bind new approval to the explicitly observed latest delivery when a persisted Render OS editing task has deliveries. Request field `expected_entrega_id` is UUID. It cannot be inferred from whatever is latest at commit. Latest means highest task_revision (then recorded_at/id deterministic tie); request task revision still required. Foreign/older/missing delivery ID rejects409; invalid UUID400. Supplying a delivery ID when task has no delivery or different scope rejects409. Tasks without deliveries retain their legacy review flow but no artifact approval is inferred.

Server emits `revision_aprobada_entrega_id` in task approval metadata only after validation. Reserve this metadata key at all browser/generic task input boundaries including creation, even admin; expected_entrega_id is request precondition, never a writable task column or metadata authority. Operational task DTO allows only UUID/null for this field. Current admin identity/session is rechecked/locked inside the same transaction before task update. Existing task-row UPDATE/CAS serializes delivery submit versus approval. Validate delivery association/latest after UPDATE while the task lock is held, before commit; mismatch rolls back task/goal/assignments and approval metadata. No additional goal/visit locks after acquiring the task.

Forward066 replaces the existing approval-invalidating trigger function (not058 historical SQL). Same previous clearing rules plus clearing delivery binding; no historical DML. A subsequent content change to finalized/legacy-completed work with a nonnull delivery binding returns it to review and clears approval/finalization/binding, without changing unbound historical completed rows on installation. Submitting a new delivery explicitly clears binding even from review with residual flags. Non-approval content/state changes cannot retain valid current artifact approval. Past event remains immutable history. Historical approved tasks without binding stay unverified, not auto-certified. A bound approval can be labelled only while task approved/finalized and server approval flag true; reopening/new version invalidates it. After-update validation must also check effective task state/flag/binding after triggers, not repair an invalidated result.

UI: editing delivery panel exposes latest ID/revision to task detail with closed callback; show explicit choice/ack naming delivered URL/version before existing “Aprobar revisión” or “Aprobar y enviar”. Never silently fetch a new delivery and approve it on behalf of the reviewer. Callback conveys selected ID, observed task revision and context; reject if parent task revision differs until deliberate refresh. Empty history uses clearly separate legacy action. Changing task/session/latest delivery resets acknowledgement. Disable approval when lookup failed/loading/inconsistent. Generic status dropdown cannot bypass server enforcement.
