# Shared audiovisual registry — integration contract

Local principal application only: React/Vite → authenticated Express API → PostgreSQL. No browser business-data store, production deployment, legacy bulk import or automatic script interpretation. Implementation readiness is determined by `PRODUCTION_REGISTRY_QA.md` and `STATUS.md`, not by this contract alone.

## Data and permissions

Forward migration 059 adds visits, normalized participant membership, individual videos and photo records. UUID identities and foreign keys preserve origin and editing-task links; restrictive deletes protect history. Every visit has an integer revision. Team members may read and record shared production content using their server-verified identity. Only current administrators may explicitly hand a video to editing. No authority comes from a display name or local profile.

Each video retains its title, script, filming result (`planificado`, `grabado`, `pendiente`, `repetir`), material link and observations. Editing task state is separate and read from the linked real task. Photo records use type, result and Drive link, not a mandatory count. Visit date and editing delivery date are different fields.

| Endpoint under `/api/producciones` | Purpose |
| --- | --- |
| `GET /?mes=YYYY-MM` | Shared calendar with visits and content summaries |
| `POST /` | Explicit new visit or reviewed link to a source visit task |
| `GET /:id`, `PATCH /:id` | Read/edit visit with expected revision |
| `POST /:id/videos`, `PATCH /:id/videos/:videoId` | Record one planned/recorded/pending/repeat video |
| `POST /:id/fotos`, `PATCH /:id/fotos/:photoId` | Record/edit a photo type and its result/material |
| `GET /pendientes` | Latest unresolved scripts, optionally filtered by client |
| `POST /:id/videos` with `video_origen_id` | Explicitly reuse a pending script in a same-client visit, preserving original history |
| `POST /:id/videos/:videoId/enviar-edicion` | Admin chooses active editor ID and manual delivery date; creates exactly one real editing task for that video |
| `GET /reconciliaciones/origen/:sourceId` | Current administrator reads closed original context and reconciliation eligibility; no writes or automatic inventory |

Nested writes and handoff require the visible visit's `expected_revision`; conflicts must not silently rebase or automatically retry. Handoff validates recorded state, usable material URL (video or visit), editor role/identity, delivery date and existing task link inside one transaction. Task insertion, normalized assignments, video linkage and visit revision form one commit. Each of three handed-off videos must produce a different task, even if recorded during the same visit.

## Source tasks and historical safety

New valid production-visit tasks can register their visit through the task persistence transaction hook. Counts and free-form source text do not invent video identities or split scripts automatically. Existing commercial tasks/records are not backfilled or rewritten.

Once a source visit task is linked, registry date/client govern that visit. An isolated source-task date/client change must conflict; explicit registry changes synchronize the source task transactionally. Editing delivery dates do not move when a visit is rescheduled. Client changes after editing tasks exist require conflict/manual review. Lock order must be source task → visit → video.

Linked sources cannot be reclassified out of the visit/workspace contract. Archiving a source does not remove the independent production history or prevent registry corrections; archived, unlinked tasks are not automatically imported. Both incoming and outgoing pending-video lineage prevent independent client changes. Explicit task reassignment/deadline changes remain possible: `editor_handoff_id` / `fecha_entrega_handoff` describe the original handoff, while `editor_actual_id` / `fecha_entrega_actual` join the current task. The UI labels these separately. A linked editing task cannot be moved to a different client by ordinary task PATCH.

The principal legacy recording/correction/confirmation and Wilson web recording paths reject mixing aggregate quantities into a visit with normalized video/photo rows. Wilson task editing uses the same transactional registry hook; supervisor date changes reject a divergent date on a linked source. These guards preserve old standalone records rather than deleting or silently converting them.

New per-video tasks use `origen_produccion_video_id` and `produccion_visita_id`, not the old per-visit aggregate `origen_visita_id` unique key. A legacy aggregate must not be silently reused, deleted or interpreted as individual videos. Any incompatible old aggregate/source logs require explicit review. Legacy endpoints remain preserved during replacement verification; their final consolidation is a separate integration gate, not proof supplied by adding these tables.

### Historical conversion boundary (integration50)

Ordinary task edits must not create a new registry from an unlinked aggregate source. The shared `hasLegacyProductionSource` predicate detects nonempty or malformed `produccion_registros`, `produccion_confirmada_at`, or an existing legacy child task with `origen_visita_id`. The task sync hook returns without conversion; metadata, counts, confirmations and children remain intact. Existing linked-visit synchronization is unchanged. Empty/null record collections without other legacy evidence still allow normal fresh registration.

Explicit POST creation with a historical source rejects409 before changing the source date or inserting a visit. This prevents creating a mixed registry whose legacy and per-video handoffs would both reject operation. It does not convert or erase an already-existing mixed registry. Existing complete aggregate legacy confirmation/single-edit flow is not retired by this protection.

At integration50, explicit reconciliation was still proposed. Integration51 implemented the bounded backend case below; integration52 adds its manual task-detail interface. Integration56 adds the explicit one-task/one-video adoption described below; true multi-video aggregate splitting and existing mixed visits remain unimplemented. Original metadata and any existing child's comments/assignments/deliveries/approvals must remain intact. Never clone one aggregate editing task across videos, erase legacy flags or globally authorize unreviewed videos after partial review.

### Explicit reconciliation backend (integration51; UI added in52)

`POST /api/producciones/reconciliaciones` requires a current database administrator, active account and matching session version, even for an idempotent replay. No query selectors accepted. Closed input: `request_id` UUID, `source_task_id`, `expected_source_revision`, `acknowledgement: 'videos_identificados_manualmente'`, visit `titulo`, optional explicit `participante_ids`/`drive_url`/`observaciones`, and1–50 explicit `videos` containing `titulo`, `estado` and optional literal `guion`/`material_url`/`observaciones`. Unknown fields, names as IDs, nulls, invalid states/URLs and oversized content reject. No quantity parser, editor selection, implicit attendees or source-content interpretation.

Eligibility: available unlinked historical visit task, active client and valid stored date, observed revision, actual aggregate evidence, no previous reconciliation, and **no legacy aggregate editing child**. Existing child or mixed/normalized visit returns409 for specific manual resolution; no clone, archive, replacement or inferred history. Date/client come from the locked source, which is not rewritten. One transaction creates the canonical visit, exactly the submitted video UUIDs, migration069 receipt and per-video provenance. It creates zero tasks, pieces, quotas or publication evidence. Manual states are declarations, not integrated filming verification; partial inventory does not claim all aggregate work was reconciled.

Response is only `{reconciliation_id,visita_id,video_ids,created}`; IDs retain explicit input order. Same actor/request and same normalized payload replays200 with original IDs, changed payload conflicts409. Unique source/visit and actor/request constraints prevent duplicates. Receipt stores hashes and source revision, not raw metadata, credentials or financial bags. App has no update/delete receipt path; immutability is application-enforced plus restrictive references, not a claimed SQL trigger.

Existing per-video handoff and editorial association accept a historical-source video only when receipt provenance matches that video/visit/source, production-history fingerprint remains unchanged and no aggregate child exists. Newly added unreviewed video UUIDs do not inherit permission. This guard does not publish a piece or waive editorial/task checks. Normal title/priority edits do not invalidate review. Client/date changes on reconciled visits return409 before any source/visit write; ordinary non-reconciled visit rescheduling remains unchanged. A later explicit re-review/rescope operation is still needed.

Source-task locking serializes legacy writers and reconciliation; actor/request advisory lock precedes source lock for replay, and current-admin row is held FOR SHARE. The rest of editorial objective/task/visit/video locking remains unchanged. Actual physical PostgreSQL tests include replay concurrency and rollback; not every possible multi-route race is certified. Migration069 is additive, with no backfill; it has only been applied to disposable test databases. Existing059 upgrade fixtures defer069 until059 exists, then execute its real SQL before current API tests.

### Manual task-detail interface (integration52)

An administrator can open **Revisar producción histórica** from an unlinked production-visit task. GET context rechecks the current DB role/activity/session in a repeatable-read snapshot (not SQL READ ONLY, because the actor row is locked FOR SHARE). It accepts a canonical numeric task ID and no query selectors. Source content is a closed literal-string projection; raw metadata/records/finance bags are never returned. Counts are labeled historical aggregates, not automatically identified videos. Oversized content returns413 rather than silently truncating the original. Eligibility distinguishes ready, aggregate editing child, existing visit, unavailable origin and non-historical source; blocked cases cannot submit.

The form begins with one blank planned video regardless of aggregate count. Operators enter each title/script/result/material manually and explicitly acknowledge the review; optional participants start empty, not inferred attendance. Original task text/material/feedback/timing remain readable and unchanged. Enter unfinished inventory in observations; partial review does not claim the remaining aggregate has been reconciled. Save creates no editing tasks or publication. Successful save refreshes the source registry link and removes aggregate recording controls; the canonical visit opens in normal Producciones/calendar/pending bank and persists on reload.

The in-memory controller freezes one serialized request+UUID across uncertain responses and retries it byte-for-byte. Definitive conflicts require explicit context reread, preserve video drafts and reset acknowledgement. Session changes, auth denial, supersession/disposal cannot publish a stale result or private context. Dirty/busy feeds the existing task navigation guard; cancelling a dirty review uses the shared discard dialog. Open review remains mounted while background registry lookup changes. Drafts are not stored in localStorage and are not promised to survive an accepted discard/browser restart. After losing an uncertain draft, a fresh context read can recover an already-linked canonical visit without creating a duplicate source.

Model tests cover errors/races; browser tests verify desktop/mobile entry, discard preservation, save, reload, pending script retention and employee control absence. No browser-injected network failure or deliberate focus/visibility matrix is claimed. No migration was applied to configured databases. Integration53 adds `contexto_historico_revisado` (boolean only) to visit detail/list DTOs. The ordinary visit form disables the reviewed date and omits it from mutable-field saves; the backend remains authoritative and still rejects effective date/client changes. A dedicated re-review/rescope interface is pending alongside aggregate-child/mixed-history resolution.

### Aggregate editing child: preservation contract before extending reconciliation

Integration55 exposes the existing editing dossier as a read-only prerequisite, **not** itself a new reconciliation disposition. Context includes `legacy_editing_tasks`, always an array of0–50 closed rows `{id,revision,titulo,estado,en_workspace}` ordered by task ID. Only current DB administrators may read it under the existing repeatable-read snapshot. It returns no raw child properties, delivery/approval clones, financial bags or caller-controlled URLs. More than50 rows returns413, never a silently incomplete list; invalid source references reject rather than fabricate IDs. Without the explicit56 adoption intent, POST still rejects every aggregate-child case.

The task-detail form renders original task references and human-readable work states; historical `publicada` is labeled historical work completion, never verified editorial publication. A `ready` response with editing children is rejected client-side. Links are derived only from validated IDs and require `en_workspace === true`, computed from the exact stored `render_os` marker. Legal old child rows without that marker remain visible as historical references with no broken workspace link. They are not reclassified, migrated or granted broader task-route access. A dedicated read-only historical evidence view/disposition is still needed for those rows. Missing optional client-side flag defaultsfalse for older responses; explicit non-booleans reject. Existing task authorization remains authoritative when a link opens.

Independent source review identifies three distinct dispositions, not interchangeable implementations: retain the aggregate as a live operational expediente and identify inventory only; explicitly adopt an existing task for ONE verified video (1:1); or replace future aggregate work with individual tasks through a separate explicit operational disposition. None is implemented by merely removing the current409 guard. First implementation must not silently choose a disposition for existing users.

Keep original task IDs, states, ID assignments, comments/activity, materials and dates. Keep delivery UUIDs and immutable editing reviews attached to their actual task/delivery; never clone an aggregate approval or interpret a textual comment author as authenticated approval. Comments do not necessarily increment task revision: a task CAS alone is not a complete immutable evidence snapshot. A future contract must specify live references or a verifiable evidence cut and handle new comments/deliveries/reviews during confirmation.

Require explicit source/child versions, ordered locks compatible with editing-operation receipts, source/child/client and editorial-link rechecks, idempotent receipts and exclusive task/video mappings. Prove rollback, replay, additional-child and concurrent-delivery/review cases, no duplicate operational work/counts and no inherited publication evidence. Multiple ambiguous children and existing mixed registries remain blocked until their disposition is explicit. This is a design constraint and implementation backlog, not a completed migration or permission bypass.

### Explicit one-task/one-video adoption (integration56)

POST's optional closed `existing_editing` is `{task_id,expected_revision,video_ordinal,acknowledgement:'esta_tarea_edita_un_solo_video'}`. Ordinal is1-based within the submitted explicit video array, whose selected entry must be `grabado`. Existing normal reconciliation intent/body/hash shape remains unchanged when the optional field is absent. User must explicitly identify the video and assert that the **entire task and all prior deliveries/corrections** refer only to it; if the task truly groups several videos this path is not applicable. It is not a way to choose one convenient version out of a multi-video history.

Requires exactly one original child across all legacy markers, matching observed child revision, active source/client/date, current admin, same client, `edicion`/`render_os`, not archived/trashed, no history/publication/goal/project/other-production binding or stale per-video markers. The child must already have one active admin/editor responsible by ID and a valid stored delivery date. No owner/date is inferred from names or filming date; users can explicitly correct the original task first, then reread and re-acknowledge. Project tasks remain protected by063's separate domain. Existing deliveries and historical completed states are allowed because they stay on the same task, not cloned or reapproved.

Global objective-link advisory precedes ordered source+child task locks and the existing source/receipt gates. One transaction creates canonical visit, explicitly declared videos,069 receipt/provenance and070 adoption mapping, sets only the selected video's existing task/editor/deadline snapshot. Source, original task, assignments, comments, deliveries, reviews, pieces and quotas are not rewritten. Response remains `{reconciliation_id,visita_id,video_ids,created}`. Same actor/request/body replay returns the same IDs after current-admin checks.070 enforces one mapping per receipt/task/video with restrictive FKs, including composite receipt/video membership; no backfill. App has no mapping-update/delete route. This records an explicit human correspondence, not an immutable snapshot of all task evidence; comments/versions continue live under the original IDs.

Later handoff/editorial mutation discovers the adopted task before taking row locks, includes it in ordered locks and rereads its mapping. The per-reviewed-video exception requires unchanged source fingerprint, the exact unique child, same receipt and intact original video/task pointer, plus current task scope/client/domain. New unreviewed videos, a later additional child, removed original marker, changed source history or invalid task scope remain denied. Original task revisions may advance legitimately through delivery/review; they are not frozen forever. Other explicitly reviewed videos can create independent editing tasks through the normal manual editor/date action. Existing task states and decisions do not create editorial publication evidence.

UI opt-in starts off, video selection starts empty and uses stable local video IDs; independent correspondence and inventory acknowledgements are required. Removing/reordering videos cannot silently change the selected identity. Source/child IDs/revisions come only from observed context; reread clears both acknowledgements, while exact uncertain retries preserve the serialized body/key. Multi-child, non-workspace, unavailable and already-linked contexts cannot use this form. Existing context DTO is not a guarantee of eligibility: server still validates stored editor/date/domain under locks.

Verified actual HTTP: preservation including delivery/approval/correction APIs, replay/rollback, invalid rows and roles, independent second-video handoff, scope/history guards, and a real PATCH-first barrier that archives the child before a concurrent handoff409/no task creation. Reverse order and editorial-specific race matrix are not certified. Migration070 has been applied only to disposable fixtures, not configured databases; deployment still needs explicit migration review/approval.

## UX acceptance

Integration54 retires implicit aggregate editing creation from the shared legacy confirmation callback (both direct HTTP and Wilson). Confirmation still validates completeness/material, source revision and mixed-registry guards, saves confirmation evidence, and returns the compatibility shape `{task,editing_task:null,created:false}`. It never chooses an editor/date, creates a task or notifies an editing assignment. The unused aggregate generator and its name-based fallback are removed. Existing aggregate children, IDs and evidence remain unchanged; their reconciliation is still blocked pending explicit disposition. Newly confirmed eligible unlinked histories use manual video identification, then the existing explicit per-video editor/date action. Wilson token/confirmation/audit atomicity remains required. UI and Mia messages distinguish confirmation from editing assignment; no response claims editing was linked merely because filming was confirmed.

Actual browser follow-up verified integration53's date protection and ordinary rescheduling: reviewed date disabled, notes saved/reloaded unchanged; mobile390px width matched document width. Native keyboard date change on a normal visit saved to22October and survived reload. Automated generic date fill changed DOM value without triggering React's native date-change path and was not counted as successful rescheduling; native ArrowUp interaction supplied the valid verification. Browser evidence predates only the last confirmation-copy edits, not a changed form layout. No production data or configured database was used.

The connected `/producciones` route appears in normal navigation and survives reload/direct links. Desktop presents calendar + selected-day agenda; mobile provides a compact readable agenda. Choosing a day shows recorded video names/results and photo types, with detail/editing available separately. Pending scripts can be deliberately resumed into another visit. Changes use backend revisions; entered drafts survive conflicts. No fictional metrics, duplicate aggregate editing task, or automatic publication may be substituted for this flow.

## Transactional request authority — integration92

`production-authority.js` replaces the registry's unguarded transaction wrapper. It captures the authenticated numeric ID/session epoch before awaiting a connection, begins READ COMMITTED, rereads that account FOR SHARE and requires the same active epoch before invoking any business callback. The row lock stays through commit. Revocation committed first denies401; a valid writer that acquired its share first commits before a conflicting account revocation can commit. Current database role, not the middleware's cached role, decides leader-only actions (403). No identity is inferred from a name.

| Routed writes | Required current authority |
| --- | --- |
| Create visit; edit visit | Active verified ID and matching epoch |
| Add/edit video; add/edit photo | Active verified ID and matching epoch |
| Send one video to editing | Same checks plus current admin role |
| Link editorial piece; link objective slot | Same checks plus current admin role |

These are nine generated concrete routes. Actor lock precedes existing objective/task/visit/video locks; existing domain lock ordering, revision checks, per-video idempotence, material/date checks and DTOs remain. No global production mutex or network call is introduced inside the transaction. Failed rollback causes the pooled connection to be discarded while preserving the original error. Early validation/role denials remain; authenticated input with no epoch cannot fall back to cached authority.

This guarantee applies to the listed HTTP registry/editorial writes. Reviewed historical reconciliation already uses its own current-admin transaction. `syncProductionVisitFromTask` remains caller-owned: no nested transaction or extra authority claim is added to task-origin writes by this patch. GETs retain their authenticated read behavior. It does not certify every writer in the system, change roles/permissions, enable cookie mode or apply a migration.

Verified disposable PostgreSQL: all nine routes reject inactive/epoch changes committed after ordinary middleware; three leader-only routes also reject an epoch-preserving downgrade. Business snapshots remain unchanged. A genuine employee still registers and cannot hand off; the inverse actor/visit lock test proves a valid handoff commits before revocation and a revoked retry cannot create a second editing task. Eleven physical production/editing suites pass152 cases, including history/reconciliation/adoption, deliveries, approvals and corrections. See integration92 in `STATUS.md` for commands, final regression counts and remaining limits. No production/configured database or real account was changed.
