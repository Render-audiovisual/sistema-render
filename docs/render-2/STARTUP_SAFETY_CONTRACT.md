# Principal startup and explicit local migrations

Local implementation contract, not a production approval. Ordinary start must not execute DDL, seeds, reconciliation, cleanup or message jobs implicitly. Existing business APIs remain writable under their normal authentication; this is startup safety, not a read-only application mode.

## Runtime

Require explicit DATABASE_URL with PostgreSQL scheme and RENDER_DB_ENVIRONMENT in development/sandbox/test/production before any startup DB query; never inherit PGHOST/PGDATABASE defaults. Parse without exposing password, raw URL, query options or secrets in diagnostics. Unknown/malformed configuration fails closed. SETUP_DEMO_DATA=true is rejected during ordinary startup; no seed function is called even in development.

Read ledger only (SELECT/to_regclass); absent ledger, pending files, unknown applied migration names or invalid ledger reject startup before listening. No table creation/repair, inferred baselines or changes to historical ledger. A healthy full schema may serve API/static files. PORT=0 is valid; log actual listening port. HOST may be set to127.0.0.1 for guarded tests; no socket opened during disabled import.

After ledger readiness, assertCoreSchemaReady performs read-only checks of minimum public auth/task/assignment/editorial/goal/production/note/receipt column types and the effective schema path. No non-catalog schema other than public may route principal queries. This is not exhaustive FK/index/trigger/data-health certification. Cast current_schemas(false) to text[] for the actual pg driver array parser.

RENDER_BACKGROUND_JOBS is an explicit comma-separated subset of editorial,trash,wilson,supervisor; default empty. Existing individual service flags remain respected. Reject unknown/duplicate values. Selected jobs require a declared nonproduction loopback target, verified actual DB identity matching the configured target, and explicit RENDER_ALLOW_BACKGROUND_WRITES=true. Production background enablement remains blocked in this local block, pending separate rollout approval. Only selected services register, including their first tick. Absent opt-in means no scheduler registration, immediate writes, purge or outbound worker. RENDER_DISABLE_SERVER_START=true preserves inert app imports for principal fixtures.

## Read-only migration inspection

backend/src/migrations.js exports readMigrationIdentity(db), readMigrationStatus(db,{deferredMigrations=[]}), buildMigrationPlan({environment,identity,status}), runMigrations(pool,logger=console,{approval,deferredMigrations=[]}={}). Identity is {database,username,address,port}. Status is {ledgerExists,applied,pending:[{name,sha256}],unknownApplied}; local filenames sorted. Inspection uses qualified public._migrations and never CREATE. Missing/incompatible ledger does not mean ready. Plan SHA256 binds normalized actual identity, environment, current ledger/status and pending SQL hashes. Errors/logs must not include connection strings or SQL data.

runMigrations rejects missing/malformed approval before connecting. Approval is explicit operator intent, not an authentication credential: {environment,expectedIdentity,planHash,purpose:'local-explicit'|'isolated-fixture',fixtureRoot?}. Never production. local-explicit requires verified loopback actual target. isolated-fixture additionally requires generated /private/tmp/render2-local-* root, matching cwd/data_directory, render2_local_test/render2_fixture identity, and an initially empty public schema. Only fixtures may supply deferredMigrations, validated against real filenames. No automatic promotion of legacy opt-in databases to trusted fixtures.

Use one dedicated client for identity verification, a chain-wide session advisory lock, fresh ledger/plan read after lock, every migration and ledger write. Revalidate approved plan after acquiring lock and before first DDL; stale plan rejects without writes. Per-file SQL+ledger transaction remains atomic. Serialize before creating _migrations, release lock safely; destroy client if lock cleanup cannot be confirmed. SQL errors become bounded migration-name errors, not raw SQL/source/credentials. No ledger ON CONFLICT used to hide duplicate execution. Deferred fixtures use actual filtered files rather than forged ledger entries.

The runner pins search_path to public only, leaving pg_catalog implicitly first for native functions while unqualified CREATE targets public. Lock timeout10s and per-statement120s bound explicit migration execution. Reset session settings before release; destroy on uncertain cleanup. Only exported controlled MigrationPolicyError instances expose a bounded filename through the CLI, never a raw driver message.

## CLI and packages

backend/scripts/migrate.js supports help (default, no DB import/connection), status and apply. Validate command/config before dynamically importing the connection pool. status is read-only and prints safe identity, pending filenames/hash and approval plan. apply requires --plan HASH --database NAME --user NAME, all matching the actual current plan/identity; environment from RENDER_DB_ENVIRONMENT must be nonproduction and target loopback. Recheck inside the locked runner; no production override. No external target contacted in verification. Missing flags never connect. No schema migration added by this code block.

backend start = node src/server.js; root start/hosting do not run migration/install/seed commands. Root migrate delegates arguments to the explicit CLI, without dependency installation. The old aggregate setup command is explicitly disabled with a clear error, preserving its legacy code as reference rather than silently creating shared leader accounts or changing client quotas. Existing explicit seed scripts are not certified safe by this block and are not invoked/recommended for Render2 rollout.

The old preview-client-goals script and legacy goal integration opt-ins must fail before connecting rather than treating a loopback URL/database name as fixture authorization; keep historical code/assertions available as reference. Principal guarded fixtures replace their execution path, not the business application. Document this limitation; do not claim old QA was successfully migrated.
