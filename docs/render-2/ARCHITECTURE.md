## Data-preserving sequence

1. Inventory schema versions and legacy identity references in an approved staging copy; obtain a recoverable backup and prove restore. Capture counts, IDs, orphan checks, monthly piece totals and financial totals before changes. No production reads/writes are authorized by this document.
2. Add nullable ID-based owner/collaborator and session/identity structures; preserve integer `usuarios.id`, client/task/piece IDs, original names, amounts, dates and JSON. If public UUIDs are needed, add unique alternate IDs, not replacement PKs.
3. Approve a mapping ledger: legacy value/record ID → person ID, evidence, approver, effective date. Auto-map only exact unambiguous approved entries. Leave collisions/shared-account history unresolved, not assigned to whoever logs in first. Retain legacy snapshots and distinguish current assignee from historical actor/payee.
4. Backfill in bounded restartable batches with conflict/orphan reports. Reconcile before/after counts and period totals; add/validate FK and uniqueness constraints after duplicates are resolved. Names/aliases may support compatibility display, never establish new access.
5. Dual-read comparison in staging, then switch authorization to ID relations. Unresolved assignments fail closed for writes while authorized historical readers retain visibility. Revoke old sessions at auth cutover; rehearse login/recovery and rollback before switching traffic.
6. Roll back application routing/feature flags without dropping additive columns or deleting new records. Keep audit and mapping ledger. Remove legacy authorization only after parity tests and owner approval.

Do not replay all historical migrations against existing data as an upgrade shortcut. `044_eliminar_tareas_finalizadas_actuales.sql` deletes published Render OS tasks; 023/026 also encode identity corrections. Fresh-schema replay is a different test from preservation of a populated upgrade. Do not invent lost rows or completion timestamps.

### Frontend cookie cutover core and remaining inventory (integration67)

`frontend/src/shared/session/browser-session-state.js` is an unmounted, dependency-injected memory observation store. It has unknown/loading/authenticated/anonymous/error states, closed frozen user/context/CSRF DTOs (no JWT), bootstrap tickets, explicit cancellation and captured intent generations. Bootstrap validates the principal response proof and rejects obsolete success/failure/401 or cancelled observations. This does not authenticate a browser by itself. Each bootstrap currently starts a new observation and invalidates old intents; it is not a transparent background refresh. Do not automatically poll/remount on focus without a reviewed same-context refresh/draft policy.

`browser-api-fetch.js` requires genuine captured intents on unsafe requests, never captures a new account at dispatch. It forbids bearer headers and API Request/URL objects or request streams (fail-closed until explicitly supported), preserves JSON/FormData/binary bodies/signals, and forces same-origin/no-store/no-redirect. Reads capture the current observation and require `X-Render-Session-Context` emitted by the backend **after current identity verification**. Cookie B/local A therefore cannot return B's body as A. Response consumers/clone and rejected network/body operations are fenced again after awaits; raw response streams are deliberately unsupported. A classified wrong-password401 preserves only its matching current observation. An obsolete401 cannot clear a new account; no cookie is cleared/refreshed and no operation is auto-retried. Proxy/DTO fences do not replace caller-side generation/dirty/CAS checks or server permissions.

These modules are not yet imported by main/App or installed as window.fetch. Principal integration tests exercise them against real fresh PostgreSQL through a simulated Node Cookie jar, not a real browser cookie policy or frontend activation. Existing browser JWT/localStorage remains until coordinated cutover, including login/logout orchestration and cross-tab login response ordering.

### Browser session operation coordinator (integration68)

`browser-session-controller.js` now supplies headless bootstrap/password-or-Google-login/logout/dispose over the67 store. It requires an injected Web Locks-compatible origin-wide exclusive manager named `render:browser-session:v1`, with no silent per-tab fallback. One lock covers challenge→cookie-setting login→proof-checked bootstrap. Login receipt ID/context/CSRF must match the actual bootstrap; fresh bootstrap role wins over the receipt's earlier role. Password/provider credential strings are only captured request bodies, never store/error/notice data. Mode/body is closed; raw transport uses only fixed API paths, same-origin/no-store/no redirects. No main/App/Login hookup yet.

Logical cancellation before verified publication stops local authentication but does **not** abort or unlock an unresolved cookie-setting request: the browser may already have installed its cookie. Dispose is not server revocation; no compensating logout may target a newer cookie. Pending-session logout cancels the observation and returns explicitly unverified, not revoked. A normal logout captures the original intent before lock acquisition, uses server context/CAS and invalidates only that intent; it never recaptures B. Cancel/dispose/busy/error paths do not automatically retry.

The verified-publication commit point distinguishes Login-page AbortSignal cleanup from explicit logout/global-controller disposal. Component abort after successful publication does not undo login. Explicit forced cancellation/disposal can withdraw only its exact published intent, including synchronous subscriber/notification/lock-release reentrancy, never a newer B observation. The coordinator must live at the application-provider lifetime; do not dispose it on ordinary Login-page navigation. UI consumers still need current-snapshot/mounted checks before routing, and must report unconfirmed logout honestly.

Notifications carry only a reason hint; the coordinator does not attach a BroadcastChannel/global listener or treat messages as identity/permission. Real cross-tab hint delivery, native Web Locks, unavailable-lock UX, page close/crash and hung-network recovery remain acceptance gates. No unsafe timeout/force-unlock of pending cookie writers is provided. Physical tests use actual principal/PostgreSQL but a simulated FIFO lock and Cookie jar, not a browser-engine proof. Do not enable the global cookie frontend until the entire earlier inventory and these lifecycle gates pass.
