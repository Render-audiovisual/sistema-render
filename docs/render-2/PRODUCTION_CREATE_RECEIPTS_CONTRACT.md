## Scope and compatibility

Canonical creation of a visit must survive an unconfirmed response without blindly producing another visit. Add optional `request_id` UUID to `POST /api/producciones`. Unkeyed existing callers keep their legacy behavior; do not manufacture or backfill keys for historical visits. The canonical frontend always supplies a key. No existing business records are merged, relabeled or deleted.

The key identifies one actor's immutable creation intent, not an authentication credential or a visit ID. The server validates the full business payload, including defaults, and hashes a deterministic canonical representation. Participant selection is set-like and canonicalized by numeric ID. Persist only actor ID, request UUID, digest, visit ID and commit time—not a copied payload or authorization snapshot.

## Transaction and replay

Use existing current actor/epoch verification under `withProductionAuthority`. Lock order: actor share lock, actor/request-specific advisory lock, existing source-task/domain resources. Receipt lookup and visit creation/participant/source effects belong to one transaction. A unique actor/request key is the database invariant, not a process-local map. Keep transactions short with no external calls.

No receipt: validate current references, create one visit and its participants, insert receipt, commit; return201 with `{visita}`. Matching receipt and digest: return200 with the current full visit, not the historic response; do not repeat source date edits, participants, creation, audit or other business mutations. Different digest with the same key:409, without changing rows. Current server authority is required for every retry; a stored receipt never revives a revoked session. Different actors do not share receipts. Rollback must remove all effects of a failed first attempt.

## Frontend

After local validation, generate one cryptographically secure UUID and freeze the exact creation payload. Double submit cannot create another in-flight intent. Do not retry automatically. An uncertain response preserves this immutable intent and exposes an explicit verification action using exactly the same key/body. Editing business fields cannot silently reuse the key or turn verification into a different creation. A complete validated response is required before the form is cleared or a detail is opened. Browser storage must not become the source of visits or pending business operations.

Intent recovery is in-memory for this scoped integration. Closing/reloading the tab can lose that recovery key; the server record remains durable, but this is not cross-device durable-draft recovery or semantic duplicate detection across independent intents. Legacy unkeyed callers also remain an explicit limitation. Do not claim broader exactly-once delivery or universal network recovery.
